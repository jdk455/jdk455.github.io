电商秒杀服务 + Agent 自动运维告警系统

本地 Docker 栈端到端搭建秒杀演示、实时聚合、全链路追踪与运维 Agent 四层闭环，共 31 个容器；完整告警到 L1 自动降级链路约 75 秒。
① 业务层：采用 Apache Dubbo 2.7.8、RocketMQ 5.0.7 与 Spring Boot 微服务，包含五个 Java 业务进程、Nginx 网关与 Nacos 注册中心，网关支持 normal、degraded、lite 三套配置模板，用于 Agent 动态限流。该层模拟真实秒杀场景下的业务流量与下单链路，是被运维的目标系统，为整个 Agent 闭环提供故障演练舞台。
② 流处理层：使用 Flink 1.18 DataStream API 与 Caffeine 维度缓存消费 RocketMQ 事件，分四路 Tumbling 窗口聚合后落库至 PostgreSQL 与 Elasticsearch。该层把异步业务事件实时转化为可被监控查询的 KPI 与明细索引，为 Agent 诊断阶段提供"业务实时数据"这第四维证据。
③ 可观测层：集成 Prometheus、Alertmanager、Grafana 与八类 exporter，并叠加 OpenTelemetry Java Agent 2.10 的字节码自动埋点与 Jaeger 后端，构成 Metrics、Logs、Trace 三支柱。该层负责采集与展示系统三支柱证据，并通过 Alertmanager 把高危告警以 webhook 投递给 Agent，是 Agent 自动化决策的触发入口与证据来源。
④ Agent 层：基于 LangGraph 的 Plan-Execute-Replan 工作流，融合四个 MCP Server 共 24 个工具，覆盖日志、指标、链路追踪与业务实时数据四个证据维度。Agent 在 P99 延迟告警下可自主选用链路追踪工具 find_slow_traces 与 span_breakdown 完成根因诊断；通过 W3C traceparent 跨 RocketMQ 异步边界把 trace_id 透传至 Flink 作业并落入 PostgreSQL transactions 表，实现从一条慢订单反查 36-span 完整调用链。该层是整个系统的"决策大脑"，承担告警接收 → 工具调用 → 根因诊断 → 分级降级的端到端闭环，把传统人工运维的多步操作压缩到一次自动决策。
⑤ 验证与总结：包含三组端到端实验、核心职责拆分、量化效果与完整技术栈。该部分覆盖功能正确性与性能表现的端到端验证，并归档项目的方法学沉淀，便于复盘与迭代。

业务层

系统整体架构
本系统通过本地 Docker Compose 编排 31 个容器，端到端复刻一套真实电商在生产环境会遇到的「流量冲击 → 监控告警 → 自动诊断 → 主动降级」闭环，整体由四个职责层（业务、流处理、可观测、Agent）+ 一个验证层组成，所有组件之间的数据流向、告警链路与降级动作都在同一份编排里跑通。

请求路径上：用户或 bash 压测脚本访问 Nginx 网关（:18080），网关将请求转发给 Spring Boot Portal 渲染秒杀页面，Portal 通过 Dubbo 调用商品（:20880）、下单（:20881）、库存（:20882）、秒杀（:20883）四个微服务，四者通过 Nacos（:8848）完成服务注册与发现。下单服务把支付成功 / 失败事件投递到 RocketMQ 5.0.7，秒杀服务从 RocketMQ 消费请求并执行限流；订单数据落到 MySQL 8.0，库存数据落到 Redis 7。网关的 normal / degraded / lite 三套配置模板，由 Agent 在故障时按策略动态切换。

流处理路径上：Flink 1.18 的 JobManager + TaskManager 以 DataStreamJob 形式订阅 RocketMQ 事件，分四路 Tumbling 窗口聚合（活动 GMV、SKU 速率、类目销售、失败率），结果按统一 schema 落到 PostgreSQL 16（聚合表，并保留 trace_id 列）和 Elasticsearch 7（明细索引）。这一层把毫秒级业务事件转化为秒级可被监控查询的 KPI 与可被反查的明细，为 Agent 提供「业务实时数据」这一独立证据维度。

观测路径上：八类 Exporter（nginx-exporter、mysqld-exporter、redis-exporter、postgres-exporter、rocketmq-exporter、cAdvisor、blackbox-exporter、Flink 自带 Reporter）把容器与服务级指标抓取到 Prometheus（:9091），Prometheus 评估告警规则后把高危告警以 Alertmanager（:9093）的 webhook 形式向外推送；Grafana（:3030）做指标可视化。同时 OpenTelemetry Java Agent 2.10 在所有 Spring Boot 进程做字节码自动埋点，trace 经 OTLP gRPC（:4317）写入 Jaeger（:16686），并通过 W3C traceparent 跨 RocketMQ 异步边界把 trace_id 透传到 Flink 作业、再写回 PostgreSQL transactions 表，实现 Metrics、Logs、Trace 三支柱 + 业务实时数据的四维证据。

决策路径上：运维 Agent 是一个 FastAPI（:9900）服务，接收 Alertmanager 的 webhook 后，由 LangGraph 调度 Plan-Execute-Replan 工作流，编排四个 MCP Server（cls :8003 日志、monitor :8004 指标、business :8005 业务数据、trace :8006 链路追踪）共 24 个工具进行根因诊断；诊断结果传给 degrade_policy 模块按 L1 / L2 / L3 等级与 cooldown 规则做策略选择，最后由 executor 通过 spawn powershell + Copy-Item + docker exec nginx -s reload 把网关切到 degraded 模板，整条链路从告警触发到限流生效约 75 秒。

Flink API 选型。Flink 作业基于 DataStream API 实现，自定义 RichSourceFunction 包装 RocketMQ 5.x 客户端完成消息消费。窗口算子选用 TumblingProcessingTimeWindows 满足秒级实时性要求；聚合算子采用 AggregateFunction 与 ProcessWindowFunction 双层结构，前者做增量累加以节省内存，后者在窗口结束时获取 windowStart 时间戳。Sink 端 PG 通过 JdbcSink.sink 配合 ON CONFLICT DO UPDATE 实现 at-least-once 语义下的幂等写入，ES 通过 IndexRequest.id 以 transactionId 作为文档主键实现幂等。Checkpoint 间隔 30 秒，配合 RocketMQ 的至少一次语义共同保障数据完整性。

字节码自动埋点。五个 Java 业务服务的 fat jar 通过 OpenTelemetry Java Agent 完成字节码层面的自动埋点，依托 Java Instrumentation API 与 Byte Buddy，在 JVM 加载类时插入 enter/exit hook，无需改动业务源码。docker compose 中加挂 javaagent jar 与若干 OTEL_* 环境变量即可启用。100% 采样下单条详情页 trace 包含 7 至 36 个 span，横跨 3 至 5 个服务。
Dubbo 调用串联。OpenTelemetry Java Agent 原生支持 Apache Dubbo 2.7+，自动产生 client 与 server 双向 span，并通过 W3C trace context 在 Dubbo 调用之间透传。一条 POST /create-order 请求实测产生 36 个 span，覆盖 portal、flashsale-server、product-server、inventory-server、order-server 五个服务的完整调用关系。
异步边界透传。RocketMQ 异步边界的 trace 透传通过两段配合完成。生产侧由 OTel Java Agent 自动将 W3C traceparent 写入 message user property；消费侧 Flink 在 RocketMQSeckillSource.parse() 中读取 msg.getProperties().get("traceparent")，按 W3C 协议解析 32-hex traceId，沿 RawSeckillEvent.traceId、Transaction.traceId、PG.trace_id 三跳链路透传至下游 sink。
持久层关联。PG transactions 表 ALTER 增加 trace_id VARCHAR(64) 列，并建立 partial index（WHERE trace_id IS NOT NULL AND trace_id 不为空）以支持按 trace_id 快速反查；同步更新 pg-init.sql 使冷启动初始化即包含该列。ES sink 通过 Jackson 序列化整个 Transaction 对象，trace_id 字段自动写入索引。
端到端验证。customer_id 为 20260505 的订单在 PG 的 trace_id 为 fc94ffc255b87bfbfc73127c4ed91adb，在 Jaeger UI 上以该 trace_id 反查可观察到 36 个 span 横跨五个 service 的完整下单链路，业务事件与调用链路在数据层实现精确关联。

整体设计。Plan-Execute-Replan 是 LangGraph StateGraph 的工程化 Chain-of-Thought，将"逐步思考"从 prompt 内的隐式过程拉到节点之间的显式状态机。
Planner 节点。使用 Qwen-Max 配合结构化 Pydantic 输出 Plan(steps: List[str])。Prompt 内置 RCA 三支柱决策树与两个示例 plan（P99 延迟告警走 trace、failure rate 告警走 error trace），引导 LLM 自主选择正确工具组合。
Executor 节点。使用 LangGraph ToolNode 与 llm.bind_tools 完成两阶段调用：先由 LLM 决定 tool_calls，ToolNode 自动执行，结果再回流给 LLM 生成最终回答。每步执行后 past_steps 通过 operator.add 累加。
Replanner 节点。结构化输出 Act(action, new_steps) 完成三选一决策：continue 继续执行、replan 替换剩余步骤、respond 生成最终响应。元 CoT 安全闸限制包括 MAX_STEPS=8 强制熔断、已执行 ≥5 步禁止再 replan、新 steps 数不超过剩余数。
Checkpointer。使用 MemorySaver 按 thread_id 持久化整图状态，使 Agent 进程异常重启后仍可续接会话；生产环境可替换为 PostgresSaver 实现跨进程持久化。
MCP 工具集分布
Logs 层 (cls_server :8003)。共 6 个工具：query_recent_logs、search_log_keyword、tail_service_log、list_log_services、get_topic_info_by_name、search_topic_by_service_name。同时支持云 CLS 与本地容器日志双模式，无云凭证时自动 fallback 至本地。
Metrics 层 (monitor_server :8004)。共 3 个工具：prometheus_instant_query 作为 Agent 直接执行 PromQL 的入口，query_cpu_metrics、query_memory_metrics 提供常用指标快速查询。模块内置关键指标白皮书覆盖 Flink、RocketMQ、PG、MySQL、Redis、Nginx、blackbox 等维度。
业务实时数据层 (business_server :8005)。共 10 个工具：get_flink_job_status、get_flink_job_backpressure、query_sku_rate、query_category_sales、query_failure_rate、query_gmv_trend、search_recent_transactions（ES）、query_inventory_status（MySQL）、query_active_flash_sales、find_traces_for_sku（业务热点与链路的跨层关联）。
Trace 层 (trace_server :8006)。共 5 个工具：find_slow_traces 用于 P99 类告警、find_error_traces 用于错误率类告警、span_breakdown 按 service 拆解耗时占比、service_dependency_graph 输出服务依赖拓扑与调用次数、query_trace_by_id 通过已知 trace_id 拉取完整链路。数据源走 Jaeger HTTP API，与 trace 后端解耦。
客户端集成。使用 langchain_mcp_adapters.MultiServerMCPClient 单例，配合指数退避重试拦截器（3 次失败后返回 CallToolResult(isError=True)）。所有 server 走 streamable-http transport（HTTP POST 与 SSE，path 为 /mcp）。

L1 自动降级。网关切换至 degraded.conf，限流由 normal 模式约 300 r/s 降至 20 r/s，burst 为 10。执行路径为宿主 Copy-Item 覆写 active.conf 与 docker exec nginx -s reload，HUP 信号热生效不掉连接，整体约 500 毫秒完成。
L2-lite 手动业务降级。切换至 lite.conf 剥图并放宽限流至 50 r/s，需经 /api/aiops/degrade/l2/lite 接口手动触发。
L2-sku_disable 单品禁用。脚本 sku-disable.ps1 修改 MySQL tech_solution_flash_sale_product 的 end_time 为过去 1 分钟，portal 立刻显示活动已结束。
L3 不可逆动作。涵盖重启服务、扩容与修改 Nacos 配置等不可逆动作，按业界共识不进入自动化策略。
Cooldown 机制。采用 key 为 level:alert_name 的双键限流，默认 5 分钟。不同 alert 之间互不干扰，例如 L1:NginxHighRequestRate 与 L1:SeckillLatencyP99High 各自独立计数。该机制可进一步演进为 (action, resource) 双键以及 MaximumAutomaticAttempts 失败熔断。
Agent Runtime 安全设计

Agent 当前通过 subprocess.run 调用 PowerShell 脚本完成降级动作，该模式在调研中被识别为高风险路径。围绕这一问题系统性梳理了业界主流安全设计方案，并明确演进路线。

能力（Capability）模型。MCP 2025-03 spec 在工具层支持 readOnlyHint、destructiveHint、idempotentHint 三档分类标注；Anthropic Claude Agent SDK 提供 permission_mode 与 Bash prefix 匹配；OpenAI Assistants API 支持 tool_choice 与 forbidden_tools。系统中 24 个工具暂以注释形式标注职责，后续将按规范打 hint。
Human-in-the-Loop runtime。LangGraph interrupt() 配合 Postgres checkpointer 将"暂停-等签名-恢复"建模为可持久化状态机；Temporal Signals、AutoGen human_input_mode、CrewAI human_input 是同类设计。相对简单 if-else，runtime 级方案天然支持跨进程恢复与超时自动 deny。
沙箱化执行。从轻到重包括专用 service account 与 AppLocker、Docker exec 进 cap-drop=ALL 与 read-only 容器、gVisor 与 Firecracker microVM、E2B 与 Modal 与 Cloudflare Sandbox SDK 等 ephemeral VM 即服务。最小成本路径为专用 service account 与 Job Object 限 CPU/Memory/进程树。
Intent-based 与 Plan-Apply。业界共识要求 Agent 不直接执行特权动作，仅产出 intent 由独立 control plane 落地。具体替换：kill -9 替换为 systemd systemctl restart 或 k8s rollout restart；改 MySQL end_time 替换为活动配置中心写入与版本化；改 nginx conf 替换为 ConfigMap 写入与 reload controller。
Write-ahead audit。tool call 进入 runtime 前先写入 pending 审计记录（输入、调用者、trace_id、计划影响面），执行完毕回填 applied 或 failed 状态。OpenTelemetry GenAI 在 2025 GA 定义 gen_ai.tool.call.id、gen_ai.tool.arguments、gen_ai.tool.result 标准 attribute。当前 _history 为内存列表，后续将持久化为 MySQL 表。
代表性研究。Anthropic Agentic Misalignment 与 Responsible Scaling 提出 least-privilege tool set 与 human checkpoint on irreversible 双原则；DeepMind CaMeL 提出将 tool call 拆为受信控制流与不受信数据流，destructive tool 仅由控制流触发；Berkeley ToolEmu 用 LLM 模拟工具执行环境进行 agent 红队测试，对应 destructive 工具必须有 sandboxed dry-run 的最佳实践。
运维 Agent 模型微调（LLaMA-Factory + DeepSpeed · 进行中）
当前状态。本节描述的领域微调工作目前正在进行中，数据集与训练流水线已搭建，正在做小规模训练与调参验证，尚未跑出最终评测数据。本节仅描述"动机 / 数据 / 训练框架 / 关键配置 / 评测计划 / 部署计划"，不展示具体的提升指标 —— 避免在结果出来之前提前虚报数字。
动机。通用大模型对运维领域的告警语义、降级动作语义与 MCP 工具选择存在偏差，直接 zero-shot 容易出现工具滥用、步骤遗漏或误降级。为提升 Agent 在 Plan-Execute-Replan 流程中的稳定性与领域准确率，构建专属微调数据集对底座模型进行领域增强。
数据构造。从历史告警到 Agent 决策到执行到报告的完整链路抽取约 2000 条 SFT 样本，覆盖告警 context 到诊断计划、工具调用参数生成、Replan 决策、L1/L2/L3 分级判定四类任务。所有样本经人工修正与对齐，构成 ShareGPT 风格的多轮对话数据。
训练框架（已搭建）。使用 LLaMA-Factory 作为统一训练入口，支持 LoRA、QLoRA 与全参三种模式切换；底层接入 DeepSpeed ZeRO-2 与 ZeRO-3，在单机多卡（2 张 RTX 4090，48GB 显存）上做 7B 级模型的领域微调；开启 gradient checkpointing 与 BF16 混合精度，预估单 epoch 训练时长约 3 小时。
关键配置（初始方案，待调参）。LoRA rank=16，alpha=32，target=q_proj/k_proj/v_proj/o_proj；学习率 5e-5（cosine 衰减）；batch size 32（per-device 4 配 gradient accumulation 8）；max length 4096，适配 Plan-Execute 多轮对话上下文；DeepSpeed ZeRO-2 与 offload optimizer 缓解显存压力。后续会按训练曲线对 rank / lr / target module 做网格调优。
评测计划（评测集制作中，尚未跑出结果）。评测维度已定义：计划准确率（Plan 阶段输出步骤覆盖标注步骤的比率）、工具选择正确率（Execute 阶段调用工具与 ground truth 一致率）、Replan 决策一致性（与人工复盘决策一致率）、L1 误降级率。当前正在制作 hold-out 评测集（从历史告警中抽取，不与训练集重叠）。具体提升数字待训练 + 评测完成后再补充到本页，不在此提前虚报。
部署计划。训练完成后将通过 vLLM 加载 LoRA 权重并与底座模型合并，对外暴露 OpenAI 兼容接口，作为 LangGraph Plan 与 Replan 节点的可选模型，与云端 Qwen-Max 形成"本地小模型快速决策 + 云端大模型兜底"的混合推理架构。

验证与总结

端到端实验与验证
实验一 · Bug 排查与修复。基线探查发现 Agent 5 次自动尝试全部失败。深挖修复三个 P0 问题。其一，缺 action_level label 时策略服务 fallback 到 L1，导致无关告警也触发自动降级，改为显式 skip。其二，PowerShell 脚本无 BOM 配 UTF-8 与中文注释，被 Windows PS 5.1 按 GBK 误解析，加 UTF-8 BOM 后解决。其三，bind-mount 配 ro 与 BusyBox cp 的限制使容器内覆写不生效，新增 active.conf 作为可写挂载点，改为宿主 Copy-Item 与 docker exec nginx -s reload 的方案。修复后 L1 首次真正在生产配置上生效。
实验二 · 注入式触发内部链路验证。绕过 Prometheus 与 Alertmanager，直接 POST context 至 /api/aiops/diagnose/context，验证 Agent 决策、policy、executor、ps1 与 conf 切换的内部链路。4 秒内观测到网关切换至 degraded 模式，conf 差异对比 MATCH，nginx -T 验证限流配置（zone=seckill_limit rate=20r/s）已生效。
实验三 · 端到端真链路生产验证。临时下调 NginxHighRequestRate 阈值至 rate 10 RPS、for 30s，用 4 路 bash 负载压网关约 280 RPS。观测到告警在 Prometheus scrape 累积后进入 pending，30 秒后转 firing，Alertmanager group_wait 10 秒后 webhook 触发 Agent 决策与执行。完整链路约 75 秒（15 秒 scrape + 30 秒 for + 10 秒 group_wait + 约 3 秒 agent）。触发详情记录 trigger_source=alertmanager 而非 manual，证明端到端链路贯通。压测共发送 2283 个请求，Agent 无误动作。
实验四 · OpenTelemetry 链路追踪集成。分七个 phase 完成。第一，下载 OTel javaagent 2.10.0（21MB，阿里云 Maven 镜像）与 Jaeger all-in-one（1panel 国内镜像）。第二，五个 Java service 加 javaagent 挂载与若干 OTEL_* 环境变量。第三，改 Flink RawSeckillEvent、Transaction、RocketMQSeckillSource、DataStreamJob，实现 W3C traceparent 跨 RocketMQ 异步边界透传。第四，PG transactions 加 trace_id 列与 partial index。第五，实现 trace_server.py 五个工具。第六，business_server 加 find_traces_for_sku 跨层关联。第七，重打 Flink jar 并重提 job。端到端验证：customer_id 为 20260505 的订单在 PG 的 trace_id 为 fc94ffc...，Jaeger 反查显示 36 个 span 横跨五个 service 的完整下单链路。
实验五 · Agent 自主调用 Trace 工具的 RCA 验证。触发 SeckillLatencyP99High 告警后，Agent 自主生成 6 步诊断计划。第一步用 Prometheus PromQL 确认 P99；第二步调用 find_slow_traces 锁定最慢 5 条链路；第三步对最慢链路调用 span_breakdown 拆耗时；第四步在 Redis 或 MQ 异常时回查 Prometheus 具体指标；第五步在 MySQL 慢查询场景下查询 mysql_global_status_slow_queries；第六步综合根因报告。第二步与第三步对 trace 工具的选用由 LLM 根据 RCA 三支柱 prompt 与工具描述自主决策完成。

整体定位。独立负责系统全栈设计、架构与落地验证。

链路追踪层。OpenTelemetry javaagent 字节码自动埋点五个 Java service，Jaeger 后端集成，RocketMQ 至 Flink 跨异步边界 traceparent 透传（手动 W3C 解析），PG transactions schema 扩展，Grafana Jaeger datasource provisioning。

调研与改进规划。系统性梳理业界 AIOps 项目（HolmesGPT、AgentCore SRE、Robusta）与 Agent Runtime 安全设计（Anthropic Capability、DeepMind CaMeL、LangGraph Interrupt、Intent-based pattern），输出 1391 行 markdown 架构报告与改进 ROI 排序。
工程验证。发现并修复 4 个 P0 bug（label fallback、PowerShell 编码、mount 与 cp 问题、nginx upstream DNS 缓存），完成 5 组端到端实验。

关键打通的链路
业务观测链。秒杀下单（RocketMQ 事件，含 traceparent）至 Flink 四路聚合（含 trace_id 透传）至 PostgreSQL（SKU、活动、类目、失败率与 transactions.trace_id）与 Elasticsearch（明细与 trace_id field）。
全链路追踪链。五个 Java service OTel javaagent 字节码埋点至 OTLP gRPC :4317 至 Jaeger collector 至 Jaeger UI :16686 与 Grafana Jaeger datasource。
跨层关联链。业务热点 SKU（business.query_sku_rate）至 ES 与 PG 查 trace_id 列（business.find_traces_for_sku）至 Jaeger 拉完整链路（trace.query_trace_by_id 与 span_breakdown），将业务热点定位与链路根因诊断串通。
告警链。八维度 exporter 至 Prometheus 17 条规则评估，Alertmanager group_wait、group_interval、repeat_interval 三层延迟控制，webhook fingerprint 去重至 Agent FastAPI。
Agent 决策链。webhook context 至 policy service 4 道闸门（enabled、action_level、cooldown、level），executor subprocess.run powershell 至 gateway 宿主 Copy-Item 与 nginx -s reload，最终落地 history 记录。
Agent 诊断链。告警 context 至 LangGraph planner（RCA 三支柱 prompt 引导 LLM 自主选择 trace 工具），生成 6 步计划，executor 逐步调用 24 个 MCP 工具，replanner 元 CoT 安全闸校验，最终生成四段式报告。
整体闭环。系统从业务事件经聚合分析与全链路追踪到自动决策的闭环完整打通，支持人工 curl 触发、告警自动触发与定时巡检三种触发模式。
