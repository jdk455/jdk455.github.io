全栈自研 · 自费部署 · 2026.04-至今

电商秒杀服务 + Agent 自动运维告警系统

本地 Docker 栈端到端搭建业务、流处理、可观测、Agent 四层闭环，共 31 个容器；完整告警到 L1 自动降级链路约 75 秒。业务层给出系统物理边界（饱和点、雪崩点、Spike 恢复时间），Agent 层给出决策能力评测（4 维 12 指标 + 4 个支撑子实验 + LoRA 三方对照）。
① 业务层 —— 电商秒杀业务全链路。Dubbo + RocketMQ + Spring Boot 微服务、Nacos 注册中心，Nginx 网关支持 normal / degraded / lite 三套配置模板。达到的效果：搭出一个可被注入故障、可被外部观测、可被 Agent 操控的真实业务运维目标；末尾用 5 阶段容量基线 SOP 测出系统真实物理边界（饱和点、雪崩点、Spike 恢复时间）。
② 流处理层 —— 把毫秒级业务事件实时变成秒级可查 KPI。Flink 四路 Tumbling 聚合后写 PG 与 ES，调用链 ID 跨异步边界自动透传。达到的效果：业务热点可一键反查到完整调用链路，为 Agent 提供 Metrics / Logs / Trace 三支柱之外的"业务实时数据"第四维证据。
③ 可观测层 —— Metrics + Logs + Trace 三支柱齐备。Prometheus + Alertmanager + Grafana + 八类 exporter，OpenTelemetry Java Agent 字节码自动埋点 + Jaeger。达到的效果：L0-L3 共 20 个分层指标 5 秒粒度采样、告警按 L1 / L2 / L3 三级分类，为 Agent 提供完整证据来源与触发入口。
④ Agent 层 —— LangGraph Plan-Execute-Replan 工作流。五个 MCP Server 覆盖日志、指标、链路、业务、拓扑五维证据，9 个处置动作对齐 OpenC2 国际标准。达到的效果：单次诊断把人工运维多步操作压缩到一次自动决策，所有决策、审批、动作、闭环验证落 audit JSONL 实现 100% 离线可重算；末尾用 4 维 12 指标 + 4 个支撑子实验量化 Agent 各部件能力。

系统整体架构

四层组件关系与数据流
本系统由四个职责层组成，每层只关注自己的核心抽象，层与层之间通过明确的"数据流契约"通信。业务层负责产生订单、库存、流量等真实业务事件；流处理层把异步业务事件实时变成秒级可查 KPI；可观测层把三支柱（Metrics / Logs / Trace）统一采集并把高危告警推送给 Agent；Agent 层接收告警、调用工具诊断、生成处置动作、把控制命令打回业务层网关形成闭环。下面的图省略每层内部的容器细节，只标注层间传输的信息类型。

可观测层 + 分析存储 → Agent。Agent 通过 5 个 MCP Server（cls 日志 / monitor 指标 / business 业务数据 / trace 链路 / topology 拓扑）调用 28 个工具进行根因诊断，每个 Server 只对接一类后端，实现单一职责与故障隔离。
Agent → 业务层（闭环回写）。诊断结论传给 degrade_policy 按 L1 / L2 / L3 等级 + cooldown 规则做策略选择，executor 通过 powershell + Copy-Item + docker exec nginx -s reload 把网关切到 degraded / lite 模板，整条链路从告警触发到控制命令落地约 75 秒。
跨层一致性 · trace_id 全链路透传。OpenTelemetry W3C traceparent 协议从 Portal 起点开始一直贯穿到 RocketMQ 消息属性 → Flink RawSeckillEvent 字段 → PG transactions.trace_id 列。任一业务热点都能在 PG 反查到完整 Jaeger 调用链，把业务诊断从经验推断变成链路证据。

业务层

秒杀商品服务链路
业务层模拟一套真实电商秒杀场景，是被运维的目标系统，也是 Agent 闭环的故障演练舞台。请求从 Nginx 网关进入 Spring Boot Portal 渲染秒杀页面，Portal 通过 Apache Dubbo 2.7.8 调用商品、下单、库存、秒杀四个独立微服务，四者通过 Nacos 1.4.2 完成服务注册与发现。下单服务把支付成功/失败事件投递到 RocketMQ 5.0.7，秒杀服务从 RocketMQ 消费请求并执行限流；订单数据落到 MySQL 8.0，库存数据落到 Redis 7。Nginx 网关支持 normal / degraded / lite 三套配置模板，由 Agent 在故障时按策略动态切换，是 Agent 闭环的执行落点。

业务层能力实测 · 容量基线 5 阶段 SOP

本节完全脱离 Agent，只回答"这套硬件 + 这套软件配置能扛多少业务流量、瓶颈在哪"。方法学对齐 k6 + Locust + Google SRE Book Ch.4 SLO 业界标准，采用 5 阶段标准 SOP 串行执行，全程 5 秒粒度采样 L0-L3 共 20 个分层指标。任务划分为：Smoke 恒定 100 RPS 5 min 定健康基线；Ramp 100→3000 RPS 阶梯爬坡找饱和点（P99>1500ms 或错误率>1% 即触发）；Spike 突跳 2000 RPS 后撤回测恢复时间；Soak 1000 RPS × 30 min 测长期稳定性；Stress 持续加压直至错误率>50% 触发雪崩判定。

反常识发现。系统在 200 RPS 饱和时 portal 容器 CPU 仅 17%、内存稳定在 404 MB / 1 GB 上限——硬件还有 80%+ 富余但 P99 已经飙到 1.5 秒以上。瓶颈不是算力，而是连接池、分布式锁、RocketMQ Producer 等并发原语。这种"硬件富余但系统已雪崩"的数据正是 Agent 介入诊断的真实价值场景，也是容量基线对 Agent 评测最大的贡献——告诉 Agent"别去查 CPU，去查并发原语"。

产物归档。每次完整跑出 bench/capacity/results/<timestamp>/ 全套产物：S1-S5 各阶段 summary.json + timeseries.csv、3800+ 个 Prom 多层指标采样、REPORT.md 容量规划表、conclusions.json 含 Agent 介入阈值建议（L1/L2/L3 分别对应饱和点的 75% / 100% / 125%）。单次实验 16000+ 真实业务请求样本可任意时刻被第三方复算。

本层从 RocketMQ 消费每一笔下单 / 支付 / 退款事件，按 10 秒滑窗实时聚合四类业务 KPI：活动 GMV（每场秒杀活动当前累计成交额）、SKU 速率（每个 SKU 每秒下单量，用于识别热点商品）、类目销售榜（各品类实时销量排序）、失败率（下单失败 / 总订单比例）。这四类 KPI 是 Agent 诊断的"业务实时数据"第四维证据，区别于传统 Metrics / Logs / Trace 三支柱。具体支撑三个 Agent 场景：Agent 看到"活动 GMV 突然不涨"立刻怀疑下单链路出问题，比看 portal P99 更直接；通过 SKU 速率发现热点 SKU，自动定位到该 SKU 在 Redis 单 key 上的雪崩风险；失败率超过 1% 触发 L2 业务降级，比"5xx 率"更贴近用户真实损失。所有 KPI 都带 trace_id，可一键反查 Jaeger 完整调用链，把业务热点诊断从经验推断变成链路证据。

技术选型：Flink DataStream API + 自定义 RichSourceFunction 包装 RocketMQ 5.x 客户端消费消息；窗口选 Tumbling Processing-Time 满足秒级实时性；聚合用 AggregateFunction（增量累加、内存友好）+ ProcessWindowFunction（窗口结束补 windowStart 时间戳）双层结构。Sink 端 PG 用 JdbcSink + ON CONFLICT DO UPDATE 做幂等写入，ES 用 IndexRequest.id = transactionId 做幂等去重；Checkpoint 30 秒一次，配合 RocketMQ 至少一次语义保证窗口重放时数据不丢不重。

字节码自动埋点。五个 Java 业务服务的 fat jar 通过 OpenTelemetry Java Agent 完成字节码层面的自动埋点，依托 Java Instrumentation API 与 Byte Buddy，在 JVM 加载类时插入 enter/exit hook，无需改动业务源码。docker compose 中加挂 javaagent jar 与若干 OTEL_* 环境变量即可启用。100% 采样下单条详情页 trace 包含 7 至 36 个 span，横跨 3 至 5 个服务。
Dubbo 调用串联。OpenTelemetry Java Agent 原生支持 Apache Dubbo 2.7+，自动产生 client 与 server 双向 span，并通过 W3C trace context 在 Dubbo 调用之间透传。一条 POST /create-order 请求实测产生 36 个 span，覆盖 portal、flashsale-server、product-server、inventory-server、order-server 五个服务的完整调用关系。
异步边界透传。RocketMQ 异步边界的 trace 透传通过两段配合完成。生产侧由 OTel Java Agent 自动将 W3C traceparent 写入 message user property；消费侧 Flink 在 RocketMQSeckillSource.parse() 中读取 msg.getProperties().get("traceparent")，按 W3C 协议解析 32-hex traceId，沿 RawSeckillEvent.traceId、Transaction.traceId、PG.trace_id 三跳链路透传至下游 sink。
持久层关联。PG transactions 表 ALTER 增加 trace_id VARCHAR(64) 列，并建立 partial index（WHERE trace_id IS NOT NULL AND trace_id 不为空）以支持按 trace_id 快速反查；同步更新 pg-init.sql 使冷启动初始化即包含该列。ES sink 通过 Jackson 序列化整个 Transaction 对象，trace_id 字段自动写入索引。
端到端验证。customer_id 为 20260505 的订单在 PG 的 trace_id 为 fc94ffc255b87bfbfc73127c4ed91adb，在 Jaeger UI 上以该 trace_id 反查可观察到 36 个 span 横跨五个 service 的完整下单链路，业务事件与调用链路在数据层实现精确关联。

Agent 拿到一条告警后要回答三个连续问题：这是什么故障（诊断）、该做什么动作（决策）、动作有没有效（验证）。一次性让大模型给最终答案做不到这件事——模型容易跳过中间步骤、瞎猜根因、忘记验证。Plan-Execute-Replan 把这条链路拆成"先规划 → 再执行每一步 → 看证据再决定继续/调整/收尾"的三节点循环，相当于把 SRE 处置故障时心里那套"先列检查清单、逐项排查、根据观察调整方向"的流程显式化成可观测、可回放、可中断的状态机。
这套架构带来四项工程能力：可追责——每一步调用了哪个工具、拿到了什么证据、为什么改写后续计划都落 audit 事件，事后任何人可重放复算；可中断——模型在 Plan / Replan 节点支持 human-in-the-loop 人工审批，L2 以上动作不能"一气呵成"自动执行；可熔断——元 CoT 安全闸（最多 8 步、5 步后禁止再 replan）避免模型陷入"反复改计划但都没用"的死循环；可替换底座——Planner / Replanner 节点都通过 model_registry 抽象切换底座，本项目就用这一点跑了 LoRA / qwen-max / base 3B 三方对照。
实现上用 LangGraph StateGraph 把工作流定义成显式状态机，三个并列节点（Planner / Executor / Replanner）共享同一个 PlanExecuteState 对象。LangGraph workflow 内部 add_node 注册 NODE_PLANNER / NODE_EXECUTOR / NODE_REPLANNER 三个节点，conditional edges 控制 Replanner 后的分支（continue / replan / respond）。Replanner 节点输出 respond 后调用 verification_service 拉 baseline / after 快照做闭环判定 —— Check 不是 LangGraph 节点而是动作 executor 内部的独立 service。

Planner 规划节点

把告警 context 翻译成 4-6 步诊断计划
· 底座：Qwen-Max（model_registry 可热切换）
· 结构化输出：Pydantic Plan(steps: List[str])
· Prompt 内置 RCA 三支柱决策树
· 两个示例 plan 引导：P99 延迟告警走 trace、failure rate 告警走 error trace
· 生成的 plan 立刻进入 audit JSONL

Executor 执行节点

逐步调用 MCP 工具获取证据
· 框架：LangGraph ToolNode + llm.bind_tools
· 两阶段调用：LLM 决定 tool_calls → ToolNode 自动执行 → 结果回流 LLM 生成回答
· 状态合并：past_steps 通过 operator.add 累加
· 工具失败指数退避重试 3 次
· 每次工具调用落 audit JSONL

Replanner 重规划节点

看证据决定 continue / replan / respond
· 结构化输出：Pydantic Act(action, new_steps)
· 三选一决策：continue 继续 / replan 替换剩余步骤 / respond 收尾
· 元 CoT 安全闸：MAX_STEPS=8 强制熔断
· 已执行 ≥ 5 步后禁止再 replan，避免死循环
· 新 steps 数不超过剩余预算
三个节点之间共享一个 LangGraph State 对象（Pydantic schema），通过 Checkpointer 按 thread_id 持久化整图状态 —— Agent 进程异常重启后仍可续接会话，生产环境可把 MemorySaver 换成 PostgresSaver 实现跨进程持久化。闭环验证（verification_service）由 degrade_action_executor 在动作落地后调用：抓 baseline + after 两次快照（间隔 verify_after_seconds）、按 recovered / partial / failed 三档判定、failed 自动触发 escalate_action（如 L1 失败升级 L2）、落 audit 的 verification.verdict 事件。
MCP 工具集分布
大模型自己不会查 Prometheus、不会读 Jaeger trace、不会跑 SQL—— 这些"取证"动作必须靠外部工具完成。MCP（Model Context Protocol，Anthropic 2024 推出的工具标准）把工具调用从"硬编码进 prompt 的字符串模板"升级为"分布式服务发现的标准协议"，让 Agent 可以像调用 microservice 一样调用工具。
Agent 排障需要五类证据：Logs（具体发生了什么）、Metrics（系统是否健康）、Trace（哪一步出问题）、业务实时数据（用户真实损失多少）、Topology（哪些服务正在跑、依赖关系如何）——经典 RCA 三支柱加上秒杀场景独有的业务实时维度，再加上拓扑发现作为前置探查。所有工具按维度拆成 5 个 MCP Server 而不是塞进一个进程，单一职责（每个 server 只懂一类后端）、独立伸缩（Logs 调用量大可单独扩容）、故障隔离（trace 后端挂了不影响 metrics 查询）、可独立替换（CLS 换 Loki 只动 Logs server）。

告警到 Agent 到降级的完整时序
从流量突发到网关被切到降级模板，端到端约 75 秒。这条链路的耗时拆解如下：15 秒 Prometheus scrape 积累指标 → 30 秒告警规则 for 条件等待避免抖动误报 → 10 秒 Alertmanager group_wait 合并同类告警 → 3 秒 Agent 完成 policy / executor 决策 → 500 毫秒网关 Copy-Item + nginx reload 热切配置。前 55 秒是观测链路本身的延迟（Prometheus + Alertmanager 工程上必要的去抖代价），Agent 决策只占其中 3 秒——瓶颈不在 Agent，而在告警系统本身，这也是后续优化的方向（缩短 scrape interval、调小 group_wait 或绕过 Alertmanager 直推 Agent）。

L1 / L2 / L3 分级决策
不是所有运维动作都同等危险。"把网关限流从 300 r/s 降到 20 r/s"是可热生效、可回滚、影响面在网关一层的低风险动作；"把 MySQL 里的活动 end_time 改到过去"会立刻关闭一整场秒杀活动、影响所有用户；"重启服务 / 扩容容器 / 改 Nacos 配置"则可能产生数据丢失或服务长时间不可用。把这三类强行打包给 Agent 一键决定，要么 Agent 太胆小放过故障，要么 Agent 太鲁莽弄出二次事故。
按可逆性切分自动化边界：L1 = 可热生效 + 可秒级回滚 + 仅影响入口流量 → 允许 Agent 自动执行；L2 = 影响整场活动或单品上下架 + 需要人工评估业务后果 → Agent 只生成动作建议、落工单等审批；L3 = 不可逆 / 涉及容量 / 涉及配置中心 → 永远不进自动化策略，必须工单 + 人工执行。该设计对齐业界 SRE 共识（Google SRE Workbook Ch.13 Managing Risk、Anthropic Responsible Scaling 的 human-in-the-loop on irreversible 原则）。
policy 引擎用四道闸门把关每一次决策：全局开关 auto_degrade enabled（紧急情况运维可一键关闭所有自动动作）、action_level 标签必须显式存在（缺标签的告警一律 skip，避免"默认 fallback 到 L1"误伤）、cooldown 窗口检查（同一类告警 N 分钟内只执行一次降级，防止抖动反复触发）、等级路由（L1 直接执行 + 落 history 与 webhook 通知，L2/L3 走工单或人工）。

L1 自动降级。网关切换至 degraded.conf，限流由 normal 模式约 300 r/s 降至 20 r/s，burst 为 10。执行路径为宿主 Copy-Item 覆写 active.conf 与 docker exec nginx -s reload，HUP 信号热生效不掉连接，整体约 500 毫秒完成。
L2-lite 手动业务降级。切换至 lite.conf 剥图并放宽限流至 50 r/s，需经 /api/aiops/degrade/l2/lite 接口手动触发。
L2-sku_disable 单品禁用。脚本 sku-disable.ps1 修改 MySQL tech_solution_flash_sale_product 的 end_time 为过去 1 分钟，portal 立刻显示活动已结束。
L3 不可逆动作。涵盖重启服务、扩容与修改 Nacos 配置等不可逆动作，按业界共识不进入自动化策略。
Cooldown 机制。采用 key 为 level:alert_name 的双键限流，默认 5 分钟。不同 alert 之间互不干扰，例如 L1:NginxHighRequestRate 与 L1:SeckillLatencyP99High 各自独立计数。该机制可进一步演进为 (action, resource) 双键以及 MaximumAutomaticAttempts 失败熔断。
Agent Runtime 安全设计

Agent 当前通过 subprocess.run 调用 PowerShell 脚本完成降级动作，该模式在调研中被识别为高风险路径。围绕这一问题系统性梳理了业界主流安全设计方案，并明确演进路线。

能力（Capability）模型。MCP 2025-03 spec 在工具层支持 readOnlyHint、destructiveHint、idempotentHint 三档分类标注；Anthropic Claude Agent SDK 提供 permission_mode 与 Bash prefix 匹配；OpenAI Assistants API 支持 tool_choice 与 forbidden_tools。系统中 28 个工具暂以注释形式标注职责，后续将按规范打 hint。
Human-in-the-Loop runtime。LangGraph interrupt() 配合 Postgres checkpointer 将"暂停-等签名-恢复"建模为可持久化状态机；Temporal Signals、AutoGen human_input_mode、CrewAI human_input 是同类设计。相对简单 if-else，runtime 级方案天然支持跨进程恢复与超时自动 deny。
沙箱化执行。从轻到重包括专用 service account 与 AppLocker、Docker exec 进 cap-drop=ALL 与 read-only 容器、gVisor 与 Firecracker microVM、E2B 与 Modal 与 Cloudflare Sandbox SDK 等 ephemeral VM 即服务。最小成本路径为专用 service account 与 Job Object 限 CPU/Memory/进程树。
Intent-based 与 Plan-Apply。业界共识要求 Agent 不直接执行特权动作，仅产出 intent 由独立 control plane 落地。具体替换：kill -9 替换为 systemd systemctl restart 或 k8s rollout restart；改 MySQL end_time 替换为活动配置中心写入与版本化；改 nginx conf 替换为 ConfigMap 写入与 reload controller。
Write-ahead audit。tool call 进入 runtime 前先写入 pending 审计记录（输入、调用者、trace_id、计划影响面），执行完毕回填 applied 或 failed 状态。OpenTelemetry GenAI 在 2025 GA 定义 gen_ai.tool.call.id、gen_ai.tool.arguments、gen_ai.tool.result 标准 attribute。当前 _history 为内存列表，后续将持久化为 MySQL 表。
代表性研究。Anthropic Agentic Misalignment 与 Responsible Scaling 提出 least-privilege tool set 与 human checkpoint on irreversible 双原则；DeepMind CaMeL 提出将 tool call 拆为受信控制流与不受信数据流，destructive tool 仅由控制流触发；Berkeley ToolEmu 用 LLM 模拟工具执行环境进行 agent 红队测试，对应 destructive 工具必须有 sandboxed dry-run 的最佳实践。
运维 Agent 模型微调 · LoRA 三方对照真实结果
设计目标。面向电商秒杀 AIOps 场景，基于 Qwen2.5-3B-Instruct + QLoRA 构建专用 RCA 诊断模型，把 Plan-Execute-Replan 主流程中的"通用大模型 zero-shot"升级为"领域微调小模型"，在结构化输出、根因诊断与工具选择三个维度形成可量化的对照实验。
动机。通用大模型对运维领域的告警语义、降级动作语义与 MCP 工具选择存在偏差，直接 zero-shot 容易出现工具滥用、步骤遗漏或误降级。为提升 Agent 在 Plan-Execute-Replan 流程中的稳定性与领域准确率，构建专属微调数据集对底座模型进行领域增强。
数据来源 · 双源构造。主源 GAIA 数据集（云智慧 CloudWise 开源，智能运维领域首个公开通用数据集，含 6500+ 指标、700 万行日志、完整 trace 调用链 + 异常注入 ground truth），辅源是本项目自有的 Alertmanager → LangGraph Plan → MCP 工具调用 → Replan → 处置报告完整链路抽取的真实样本，合计约 2000 条 ShareGPT 风格多轮对话数据。
为什么选 GAIA。三模态（metric / log / trace）完整覆盖，与本项目 Prometheus + 本地日志文件（可选阿里云 SLS）+ Jaeger 可观测栈天然同构；异常注入有 ground truth，监督样本可从原始数据 + 注入记录自动推导；MicroSS 仿真平台是 Spring Cloud 微服务，注入故障模式（服务限流、数据库慢查、缓存击穿）与秒杀场景高度重合。
训练配置 · 真实跑通。LLaMA-Factory + QLoRA，rank=16、alpha=32、target=q_proj/k_proj/v_proj/o_proj，学习率 2e-4 配 cosine 衰减，bf16 混合精度，3 epochs，cutoff_len=4096。单卡 vGPU 48GB，train_loss 收敛到 0.0674，wall clock 14:59 min，无 OOM。
评测方法 · 9 维 rubric。构建 rubric-based 评分框架，对齐 AIOpsLab + SRE Book Ch.14 incident postmortem 6 要素。9 个指标分三组：结构维度（structure_coverage / structure_strict_parse / response_time）、内容维度（fault_class_accuracy / root_cause_concept_recall / evidence_grounding / hallucination_rate）、处置维度（action_alignment / verification_foresight）。对 5 类秒杀域故障各写 gold answer rubric，三方对照自研 LoRA / Base Qwen2.5-3B / 云端 qwen-max。

Agent 能力评测 · 4 维度 12 指标

给定一个真实告警，Agent 能否正确诊断、正确处置、真正让业务恢复——这是评测的核心问题。指标体系对齐 AIOpsLab benchmark / τ-bench / RCAEval / Google SRE Book Ch.14。所有结论基于 append-only 的 audit JSONL 实现 100% 离线可重算：每次 Agent 运行落 6 类事件（policy.decision / approval.created / approval.resolved / action.executed / verification.verdict / agent.response_generated），任何第三方在数天后都能拷贝产物原样复算。

Dim A 诊断准确性。A1 RCA Hit Rate（诊断结论是否命中真实根因，LLM-as-judge 对比 ground truth）/ A2 Tool Selection Recall（期望工具被调用比例，path-based 按 4 条诊断路径计算）/ A3 False Root Cause Rate（误诊率）。
Dim B 处置有效性。B1 Action Correctness（执行动作是否在期望集合内）/ B2 Business Recovery Rate（动作后业务指标是否回到 SLO）/ B3 Over-action Rate（不必要的处置数）。
Dim C 时效性。C1 MTTD（告警 firing 到诊断报告生成）/ C2 MTTR（告警 firing 到业务指标恢复）/ C3 Decision Latency（Plan + Execute + Replan 纯计算耗时）。
Dim D 安全合规。D1 Approval Compliance（L2+ 动作是否走审批）/ D2 Sandbox Coverage（subprocess 是否经沙箱）/ D3 Rollback Readiness（失败动作是否触发回滚或升级）。D 维度为本项目原创，业界主流 benchmark（AIOpsLab 等）尚未覆盖安全合规。

端到端实验与验证
实验一 · Bug 排查与修复。基线探查发现 Agent 5 次自动尝试全部失败。深挖修复三个 P0 问题。其一，缺 action_level label 时策略服务 fallback 到 L1，导致无关告警也触发自动降级，改为显式 skip。其二，PowerShell 脚本无 BOM 配 UTF-8 与中文注释，被 Windows PS 5.1 按 GBK 误解析，加 UTF-8 BOM 后解决。其三，bind-mount 配 ro 与 BusyBox cp 的限制使容器内覆写不生效，新增 active.conf 作为可写挂载点，改为宿主 Copy-Item 与 docker exec nginx -s reload 的方案。修复后 L1 首次真正在生产配置上生效。
实验二 · 注入式触发内部链路验证。绕过 Prometheus 与 Alertmanager，直接 POST context 至 /api/aiops/diagnose/context，验证 Agent 决策、policy、executor、ps1 与 conf 切换的内部链路。4 秒内观测到网关切换至 degraded 模式，conf 差异对比 MATCH，nginx -T 验证限流配置（zone=seckill_limit rate=20r/s）已生效。
实验三 · 端到端真链路生产验证。临时下调 NginxHighRequestRate 阈值至 rate 10 RPS、for 30s，用 4 路 bash 负载压网关约 280 RPS。观测到告警在 Prometheus scrape 累积后进入 pending，30 秒后转 firing，Alertmanager group_wait 10 秒后 webhook 触发 Agent 决策与执行。完整链路约 75 秒（15 秒 scrape + 30 秒 for + 10 秒 group_wait + 约 3 秒 agent）。触发详情记录 trigger_source=alertmanager 而非 manual，证明端到端链路贯通。压测共发送 2283 个请求，Agent 无误动作。
实验四 · OpenTelemetry 链路追踪集成。分七个 phase 完成。第一，下载 OTel javaagent 2.10.0（21MB，阿里云 Maven 镜像）与 Jaeger all-in-one（1panel 国内镜像）。第二，五个 Java service 加 javaagent 挂载与若干 OTEL_* 环境变量。第三，改 Flink RawSeckillEvent、Transaction、RocketMQSeckillSource、DataStreamJob，实现 W3C traceparent 跨 RocketMQ 异步边界透传。第四，PG transactions 加 trace_id 列与 partial index。第五，实现 trace_server.py 五个工具。第六，business_server 加 find_traces_for_sku 跨层关联。第七，重打 Flink jar 并重提 job。端到端验证：customer_id 为 20260505 的订单在 PG 的 trace_id 为 fc94ffc...，Jaeger 反查显示 36 个 span 横跨五个 service 的完整下单链路。
实验五 · Agent 自主调用 Trace 工具的 RCA 验证。触发 SeckillLatencyP99High 告警后，Agent 自主生成 6 步诊断计划。第一步用 Prometheus PromQL 确认 P99；第二步调用 find_slow_traces 锁定最慢 5 条链路；第三步对最慢链路调用 span_breakdown 拆耗时；第四步在 Redis 或 MQ 异常时回查 Prometheus 具体指标；第五步在 MySQL 慢查询场景下查询 mysql_global_status_slow_queries；第六步综合根因报告。第二步与第三步对 trace 工具的选用由 LLM 根据 RCA 三支柱 prompt 与工具描述自主决策完成。
核心职责
整体定位。独立负责系统全栈设计、架构与落地验证。
业务层。基于 Apache Dubbo 2.7.8、RocketMQ 5.0.7 与 Spring Boot 的秒杀微服务架构，含五个 Java 业务进程，网关三套配置模板（normal、degraded、lite）的参数调优。
流处理层。Flink 1.18 DataStreamJob 的四路聚合拓扑、enricher（Caffeine 10min 缓存）、dedup（ValueState）以及 sink 至 PG 与 ES 的并发与幂等性保证（ON CONFLICT 与 IndexRequest.id）。
可观测层。八维度 exporter、17 条告警规则、L1/L2/L3 分级与 action_level 标签体系，Alertmanager 的 group_wait、group_interval 与 repeat_interval 路由策略。
链路追踪层。OpenTelemetry javaagent 字节码自动埋点五个 Java service，Jaeger 后端集成，RocketMQ 至 Flink 跨异步边界 traceparent 透传（手动 W3C 解析），PG transactions schema 扩展，Grafana Jaeger datasource provisioning。
Agent 运维层。LangGraph Plan-Execute-Replan 三节点工作流与状态转移设计，28 个 MCP 工具的接口与权限模型(5 个 Server)，degrade_policy_service 的 4 道闸门与 cooldown 双键设计，verification_service 三档闭环判定，脚本化执行器（PowerShell 跨平台适配），history 表与审计日志。
Agent 决策层。Planner prompt 内置 RCA 三支柱决策树与示例 plan，Replanner 元 CoT 安全闸（MAX_STEPS、replan 限制），Pydantic 结构化输出强约束。
调研与改进规划。系统性梳理业界 AIOps 项目（HolmesGPT、AgentCore SRE、Robusta）与 Agent Runtime 安全设计（Anthropic Capability、DeepMind CaMeL、LangGraph Interrupt、Intent-based pattern），输出 1391 行 markdown 架构报告与改进 ROI 排序。
工程验证。发现并修复 4 个 P0 bug（label fallback、PowerShell 编码、mount 与 cp 问题、nginx upstream DNS 缓存），完成 5 组端到端实验。

关键打通的链路
业务观测链。秒杀下单（RocketMQ 事件，含 traceparent）至 Flink 四路聚合（含 trace_id 透传）至 PostgreSQL（SKU、活动、类目、失败率与 transactions.trace_id）与 Elasticsearch（明细与 trace_id field）。
全链路追踪链。五个 Java service OTel javaagent 字节码埋点至 OTLP gRPC :4317 至 Jaeger collector 至 Jaeger UI :16686 与 Grafana Jaeger datasource。
跨层关联链。业务热点 SKU（business.query_sku_rate）至 ES 与 PG 查 trace_id 列（business.find_traces_for_sku）至 Jaeger 拉完整链路（trace.query_trace_by_id 与 span_breakdown），将业务热点定位与链路根因诊断串通。
告警链。八维度 exporter 至 Prometheus 17 条规则评估，Alertmanager group_wait、group_interval、repeat_interval 三层延迟控制，webhook fingerprint 去重至 Agent FastAPI。
Agent 决策链。webhook context 至 policy service 4 道闸门（enabled、action_level、cooldown、level），executor subprocess.run powershell 至 gateway 宿主 Copy-Item 与 nginx -s reload，最终落地 history 记录。
Agent 诊断链。告警 context 至 LangGraph planner（RCA 三支柱 prompt 引导 LLM 自主选择 trace 工具），生成 6 步计划，executor 逐步调用 5 个 MCP Server 下的工具，replanner 元 CoT 安全闸校验，最终生成四段式报告。
整体闭环。系统从业务事件经聚合分析与全链路追踪到自动决策的闭环完整打通，支持人工 curl 触发、告警自动触发与定时巡检三种触发模式。
